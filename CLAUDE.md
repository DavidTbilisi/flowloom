# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

flowloom is a **text-first systems-thinking studio** (Vensim-style stocks/flows/loops) that runs in the browser. The plain-text `.flow` model is *canonical*; the diagram, plots, and animation are all derived from it. The design goal is that an AI can read and edit a model entirely as text. See `README.md` and `docs/` for the full picture.

## Commands

|---|---|
| `npm run dev` | Vite dev server (HMR). |

| `npm test` | Vitest contract tests (Node, `tests/unit`). `npm run test:watch` to watch. |

| `npm run test:all` | Both suites. |
| `npm run gen:examples` | Regenerate `examples/*.flow` from the canonical embedded source. |
| `npm run build:cli` | Compile the `flowloom` CLI to `dist-cli/` (real Node ESM). Also runs on `prepare`, so `npm i -g .` / `npm link` builds the bin. |

Run a single unit test file: `npx vitest run tests/unit/engine.test.ts`. A single e2e test: `npx playwright test -g "playback advances"`.

## Architecture (the data flow)

`text (.flow)` → **`src/lang`** parses to a `Model` (AST) → **`src/engine/compile`** expands delays into internal stocks → **`src/engine/codegen`** lays names out at fixed `Float64Array` slots and compiles each expression once (`SimPlan`) → **`src/engine/simulator`** integrates (Euler/RK4) to a `SimResult` → **`src/ui`** renders plot, animated diagram, table, loops. `src/engine/loops` derives the signed influence graph for R/B loop detection. Full version: `docs/architecture.md`.

Three layers, strictly separated:
- **`src/lang`** — tokenizer, Pratt expression parser (`expr.ts`), line-grammar model parser (`parser.ts`), shared `types.ts`. **No `eval`/`new Function`** — expressions are an inspectable AST interpreted by `src/engine/eval.ts`. This is deliberate (safety for AI/shared model text, plus dependency extraction and numeric differentiation).
- **`src/engine`** — pure TypeScript, **no DOM imports**, so it runs in Node (tests) and the CLI. Integrator, builtins, delay/lookup handling, loop analysis.
- **`src/ui`** — the only DOM-aware layer. `store.ts` is the observable state; `app.ts` wires everything and owns the single `requestAnimationFrame` animation clock.

## Things to know before editing

- **Keep `src/engine` and `src/lang` DOM-free.** Their portability to Node is what makes the contract tests and the CLI possible. If you import from `src/ui` into them, you break this — and the CLI's `tsconfig.cli.json` build (which compiles only the graph reachable from `src/cli.ts`) would start pulling in the DOM.
- **Stateful builtins are compiled, not interpreted.** `smooth*`/`delay1`/`delay3` are rewritten into internal stocks in `compile.ts` (named `delay#N`, which can't collide with user identifiers). That's why they integrate correctly under RK4 and show up as nodes in the loop graph. Stateless functions live in `builtins.ts`.
- **Fixed delays are owned by the integrator, not by a backend.** `previous(X)` / `delay_fixed(X, n)` are *pipeline* delays (the value exactly n steps ago), which no stock can express. `compile.ts` turns each call into a `FixedDelay`: the input becomes an internal aux (`prev#N.in` / `fixed#N.in`, `isInternal`, appended after every user var) and the output is a plain scope slot (`prev#N` / `fixed#N`). `runIntegration` (codegen.ts) keeps one ring buffer per delay, fills the output slot *before* each step's first `deriv` and records the sampled input *after* it — so the value is held across RK4 sub-stages and the TS and WASM backends agree by construction (they only ever read the slot). Lengths are read once at `t=start`, rounded to whole steps, minimum 1. The default init is the input's own initial value; if the input depends on the delay's output the fixed-point init can't settle — `initStateInto` returns `false`, `runPlan` attaches a note, and `lint` (`checkCircularInit`) says it statically. `src/lang/expr.ts`'s `instantVars`/`TIME_CROSSING` is what lets the parser's topological sort see *through* a delay's input (so `a = previous(b)`, `b = a+1` is not an algebraic loop); keep it in sync with `STATEFUL` in `builtins.ts`.
- **`sim method=map` is a difference equation, decided in one place.** `runIntegration` steps the first `plan.userStates` states by `+ k1` (change() is a per-step increment in the stock's own units, no `× dt`) and the remaining internal smooth/delay states by `+ dt·k1` (their time constants stay in time units). Nothing else in the engine branches on `map`: the units check (`checkUnits`) expects `change(stock)` in stock units rather than stock/time, and `checkDiscreteTime` (lint) recommends `map` for clock-on-the-grid models and flags a leftover `/ dt` inside a `change()`. `euler dt=1` with per-time-unit flows gives the same numbers; `map` is what makes the text say what the model is. If a future backend ever owns the integration loop, the user-vs-internal split has to travel with it.
- **Loop enumeration is capped; the basis is not.** `findLoops` (loops.ts) enumerates simple cycles with a work cap (`MAX_LOOPS`, `MAX_TRAVERSALS`). `sils.ts` computes the shortest independent loop set independently of it: Tarjan SCCs → cycle rank (E − N + 1 per SCC) → Horton's candidate set (for every node v and edge x→y in the SCC, v ⇝ x → y ⇝ v along BFS shortest paths; lengths from distance tables so candidates sort before any path is built) → greedy GF(2) elimination on link-incidence bitsets (`bigint`) until the rank is met. With a `dead` predicate (links flat at every sample, passed from `analyzeLoops`) live candidates are generated over live links and ranked first — still a basis, reads as this run's structure. `analyzeLoops` marks matching enumerated loops `independent` and *appends* basis loops enumeration missed (only when capped), so `rep.independent === rep.rank` is the invariant; `loopKey` (rotation-canonical node string) is how loops are matched, here and in diff.ts.
- **`expect` lines and `diff` are the two halves of "refactor safely".** `expect [SCENARIO] METRIC OP VALUE [± TOL]` is parsed in `parser.ts` (`parseExpect`/`validateExpects` — the scenario token is the one without a colon; series names are checked against stocks + non-param vars; `METRIC_OPS`/`LOOP_METRICS` are exported so nothing else hard-codes the list) and run by `engine/expect.ts` (`runExpects`: one simulation per scenario, `judge` is pure, `loops:*` metrics go through `analyzeLoops`). `engine/diff.ts` (`diffModels`) compares two models as structure → series on the shared time grid → live-loop census; `identical` is numbers + live loops only, by design — structure changes are listed, not failed. Both exit non-zero from the CLI (`test`, `diff`) so a model can sit in CI. The budget example carries real expects: when a number from a model is cited anywhere (a wiki page, a README), write the expect first.
- **`switch` is a param with `boolean: true`, not a new kind.** Every consumer that treats `kind === "param"` as a knob keeps working; the flag is what `sensitivity` (off→on instead of ±frac), `global-sensitivity` (sampled as {0,1}, Morris flips), the Tune panel (a toggle), `setParamValue` (writes on/off), and `applyOverride` (accepts on/off, rejects 0.5) branch on. The parser rejects any value that isn't 0/1/on/off/true/false/yes/no.
- **`const` is a param with `constant: true`.** Same maths; `knobParams` (grain.ts) is the one place that decides what sensitivity / global sensitivity vary by default, and the Tune panel and Calibrate skip consts too. Naming a const explicitly (`--param yearLen`) still varies it.
- **Time-grain knobs (grain.ts).** `timeGrainParams` statically finds params that are read on the time grid — `delay_fixed` lengths, anything compared/`%`-ed with `t`, `step`/`pulse`/`ramp` times — by collecting the names in those contexts and closing backwards through the vars. `sensitivity` bumps them by ≥ `dt` (row `step`), `global-sensitivity` snaps their samples to multiples of `dt` and Morris steps them by one grain (else the sample snaps back and the effect reads 0). A row whose bump changes nothing is marked `flat`.
- **`policies` (policies.ts) enumerates 2^n switch combinations** — default set = switches that are *off as written* (the moves available; on-as-written switches are facts of the world). `values[mask]` is the whole table; best / cheapest-to-target / exact Shapley (`φ_i = Σ |S|!(n−|S|−1)!/n! · Δ`) are read off it. Cap 12 switches. The MCP tool trims `combos` when the table is long.
- **`# @rung N` is parsed off doc comments** (`extractRung` in parser.ts) into `VarDecl.rung` / `ScenarioDecl.rung`; the tag is removed from `doc`. `leverage.ts` (`leverageLadder`, `MEADOWS_RUNGS`) groups tagged levers by rung and measures them through `sensitivity` (params/switches) and `compareScenarios` (scenarios). The Tune panel sorts knobs by rung and inserts `.tune-rung` headers when any knob is tagged.
- **The scenarios table (`#scTable`, app.ts `renderScTable`)** runs `compareScenarios` on `parseModel(store.source)` — the *un-overridden* text, since `store.run.model` already carries the active scenario — for final/min/max of up to four visible series, only while open, keyed by a (source, scenario, visible) signature; a generation counter drops superseded results; models with ≥120 stocks are declined. E2E coverage for switches/scenarios/table/loops/rungs lives in `tests/e2e/scenarios.spec.ts`.
- **`link A -> B ±` lines are declared edges (`Model.links`, carried on `Compiled.links`).** The parser accepts a stockless model when it has links; `structure()` in loops.ts adds link endpoints as nodes *before* reading equation edges (so a param named in a link becomes a node) and appends declared edges whose sign `readSigns` returns verbatim; `Edge.declared` marks them so `dominance.ts` skips them and the UI can tell. A stateless plan runs to an empty result with a "qualitative sketch" note (`simulator.ts`); `analyzeLoops` samples once for it.
- **Scenarios are text; the active choice is view state.** `scenario NAME k=v …` lines parse into `Model.scenarios` (validated at parse time — unknown key, bad value, reserved `base`). `applyScenario` (overrides.ts) is just `applyOverride` per binding, so a scenario can do exactly what `--set` can. The CLI/MCP apply `--scenario`/`scenario` *before* `--set`; `compareScenarios` (compare.ts) runs base + each scenario and reduces to metrics. In the studio `store.scenario` is UI state like the overlays (the text stays canonical), `build()` applies it after parsing, and — for small models — overlays the un-overridden run as `overlay.compare` with `label: "base"`. A Tune knob bound by the active scenario writes to the scenario line (`setScenarioValue`), not the param line.
- **Bare numeric literals are unit-polymorphic in `units.ts`** (`LITERAL`, alongside `UNKNOWN`): `Cash < 0`, `max(0, x)`, `t % 12` never warn on their own. A literal becomes a pure scalar under `*`//`; elsewhere it adopts the other operand's dimension. A missing optional argument is `LITERAL`, not dimensionless.
- **Three simulation backends, one `SimPlan`, identical numbers.** The hot path is `src/engine/codegen.ts`: `buildPlan` assigns every name a fixed slot in one reused `Float64Array` and `compileWith` compiles each expression once (no per-step allocation, no string scope). `eval.ts` (the old tree-walker) is retained only for `loops.ts` perturbation — don't route simulation through it. For very large models the same plan is lowered to a WebAssembly module (`src/engine/wasm/`, hand-emitted bytecode — keeps the no-`eval` property) and run via `simulateAsync`; the TS backend is the default and the fallback. **All three must produce identical output** — `engine.test.ts` pins the TS path to closed-form solutions and `wasm.test.ts` pins WASM to the TS path; treat any divergence as a bug, not rounding. The WASM imports in `wasm/backend.ts` must replicate `builtins.ts` exactly.
- **The diagram is a pan/zoom infinite canvas (`src/ui/diagram.ts`).** Nodes are laid out in a *virtual* coordinate space sized to the node count (radial for small graphs, grid for large); a viewport `<g>` transform does pan/zoom. Keep these separate: `render()` rebuilds the SVG (structural/animation), `applyTransform()` only updates the viewport transform — pan/zoom must never trigger a rebuild, or large graphs stutter. Rendering degrades by node count (`ANIM_LIMIT`/`FULL_LIMIT`/`EDGE_LIMIT`): full animated boxes → static boxes → dot-map → edges omitted. Per-frame animation runs via `tick()` only below `ANIM_LIMIT`.
- **Large models run in a worker (`src/ui/sim-worker.ts`).** The store offloads runs above a size threshold so the UI stays responsive; this only works because `src/engine`/`src/lang` are DOM-free. If you add engine imports, keep them DOM-free or the worker (and Node tests) break. The Vite config sets `worker.format: "es"` because the worker dynamically imports the WASM backend.
- **The CLI (`src/cli.ts`) and the MCP server (`src/mcp.ts`) are headless consumers**, alongside the Node tests and the worker. Both import *only* the `src/engine`/`src/lang` barrels (never `src/ui`) and run the same parse → compile → `simulateAsync` → render pipeline as the browser, so the numbers match by construction. They build separately from the web app: `tsconfig.cli.json` emits `cli.ts` **and `mcp.ts`** plus the reachable engine/lang graph to `dist-cli/` as Node ESM (the `.js` import extensions already in source are what make that resolve at runtime). CLI `run`/`loops`/`check`/`describe`/`explain`/`reference` and the MCP `flow_*` tools mirror studio features; `--set k=v` (CLI) / `set` (MCP) rewrites a param/stock-init/sim-setting on the parsed `Model` before running via the shared `applyOverride` (`src/engine/overrides.ts`) — an AST edit, keeping the text-canonical spirit. If you reach into `src/ui` from the engine/lang, the web app may survive but `npm run build:cli` breaks. The MCP server is flowloom's only runtime dependency (`@modelcontextprotocol/sdk` + `zod`); the rest of the package stays dependency-free.
- **The agent-facing reference has one DOM-free source.** `src/engine/reference.ts` (`REFERENCE`) is the catalog of every keyword/builtin/const — signature, summary, arity — shared by the CLI (`reference`), the MCP `flow://reference.json` resource, the generated `docs/llms.txt` (`npm run gen:llms`, via `scripts/gen-llms.ts`), **and** `src/ui/help-content.ts`, which derives its status-bar entries from it so the editor help and the agent reference can't drift. `src/engine/introspect.ts` (`describeModel`/`explainModel`) is the shared structure/summary view behind CLI `describe`/`explain` and the matching MCP tools. Coverage is gated by `tests/unit/reference.test.ts` and the existing `help.test.ts`; `tests/unit/llms.test.ts` keeps `docs/llms.txt` fresh.
- **The text is the single source of truth.** UI controls that change settings rewrite the `sim` line via `src/ui/model-edit.ts` rather than holding separate state. Preserve that invariant. Plot *overlays* (`store.overlay`: Monte Carlo bands, a loaded `Dataset`, a comparison run) are the one bit of UI-only state that isn't derived from the canonical text — they're auxiliary visuals drawn over the run, not part of the model. The exception that proves the rule is **Calibrate**, which fits params and writes the results *back into the text* via `setParamValue` (`model-edit.ts`) so the model stays canonical. Bands are cleared whenever the model rebuilds (they belong to the prior run); a loaded dataset and comparison persist across edits.
- **Loop polarity is read along the trajectory (`loops.ts`).** `analyzeLoops` runs the model once through `runPlan` with an `onStep` hook (codegen.ts `runIntegration`'s 4th arg) capturing the full scope vector at up to 64 steps, then reads every link's sign at each sample by central-difference perturbation (`readSigns`); structure (`structure`) is read once. A loop's `polarity` is the start reading when it is active there (the contract tests pin logistic = R), else the first active reading (`resolvedAt`), else "?" — and "?" now means *inactive in this run* (`active:false`, `deadLinks` = links zero at every sample), not "couldn't tell". `flips` marks R↔B along the run; `trace` is the per-sample reading. `influenceGraph(model)` (start signs) still feeds the diagram. The map idiom `change(X) = (next − X)/dt` is recognised (`isMapAssignment`) and its self-link dropped. `dominance.ts` (`loopDominance`) ranks active loops by knockout: freeze one user-level link (`cutLink`, an AST edit on a clone — the link shared by the fewest active loops) at its start value, re-run, Δ on the metric; `runaway` when the cut sends the metric off the scale.
- **Randomness is a *counter-based* PRNG, resampled once per step.** `random`/`random_uniform`/`random_normal` are pure hashes of `(seed, step, draw-index)` (`src/engine/rng.ts`), not a stream with hidden state — so the value is identical across RK4's four sub-stage `deriv` calls (the integrated vector field stays well-defined) and bit-identical across all three backends. Seed (`sim seed=`, default 0 ⇒ reproducible) and the integer step live in two reserved scope slots (`#seed`/`#step`, written by `runPlan`/`runIntegration`); each call site gets a stable draw index assigned in `buildPlan`. The WASM backend *imports the same `rng.ts` functions* rather than re-deriving them in bytecode, which is what guarantees parity (`wasm.test.ts`). The tree-walker (`eval.ts`, loop analysis only) returns the distribution mean instead, since perturbation wants a deterministic operating point. `src/engine/ensemble.ts` (`monteCarlo`) runs N seeds and reduces to percentile bands, mirroring `sweep.ts`.
- **Units checking is opt-in dimensional analysis.** `src/engine/units.ts` (`checkUnits`, called from `lintModel`) infers a dimension over the `Expr` AST from `[unit]` annotations. An *un-annotated* name is UNKNOWN (contagious, silent), not dimensionless — so it only warns where the user annotated enough to make a claim. All warnings, never blocks a run. DOM-free like the rest of `src/engine`.
- **Examples are generated, not hand-maintained.** The canonical copy is `src/examples/index.ts` (embedded so the app needs no network); `examples/*.flow` are produced by `npm run gen:examples`. Edit the source, then regenerate — don't edit the `.flow` files directly.
- **Tests are contracts.** Unit tests pin language semantics and numeric output against closed-form solutions / invariants; changing them is a deliberate language change, not a refactor. The app exposes its store on `window.flowloom` for e2e and tooling.
- **The help/learning subsystem is derived from the model, like everything else.** `src/ui/highlight.ts` is a *pure, lossless* tokenizer (its tokens must rebuild the source verbatim) used both to paint the editor overlay and to find the token under the mouse; keep it DOM-free so it stays unit-testable. `src/ui/help-content.ts` resolves identifier help straight from the parsed AST — a contract test (`tests/unit/help.test.ts`) asserts every keyword/builtin/reserved name has an entry, so extending the language without adding help fails CI. Contextual help flows to one bottom status bar (`statusbar.ts`) via a single `[data-help]` delegation; the editor (`editor.ts`) feeds it directly. The editor overlay is a `<pre id="hl">` layered behind a transparent-text `<textarea>` — the two **must** share every CSS metric (font, padding, `white-space`, `tab-size`) or the colors drift off the characters. Guided learning (`tour.ts` engine + `tutorials.ts` content) drives the real studio through a small `TourCtx` and rewrites the canonical text exactly like the toolbar — lesson steps validate against the live `store.run`.
